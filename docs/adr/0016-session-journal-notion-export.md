# ADR 0016: Журнал аналитических сессий (SQLite) и экспорт в Notion

- **Статус:** принято
- **Дата:** 2026-11-22
- **Этап:** наблюдаемость сессий + внешняя витрина отчётов
- **Связанные решения:** [ADR 0009](0009-mcp-facade.md) (MCP-фасад), [ADR 0013](0013-langgraph-hybrid-contract.md) (статусы решения), DECISIONS #19/#21 (лимиты и деградация)
- **Связанные документы:** `.mcp_state/audit.jsonl` (существующий аудит), `docs/LLM_CALLS.md`
- **Затрагивает:** `src/onec_analyst/session_log.py` (новый), `app.py`, `app_local.py`, `scripts/notion_export.py` (новый), `tests/conftest.py`, `.gitignore`, `.dockerignore`, зависимости

## Контекст

Аудит MCP (`audit.jsonl`) пишет **шаги** обработки: статус, интент, число вызовов LLM,
длительность узла. По нему нельзя ответить на продуктовые вопросы «сколько сессий
закончилось результатом», «как долго ждёт пользователь», «какая доля ответов
деградировала до правил»: события не связаны в один запрос и не содержат ни DSL,
ни вердикта.

Нужен второй, независимый канал: одна строка = один запрос пользователя, с итогом
и метриками. Требования:

* запись не должна влиять на ответ (fail-safe), не должна вызывать сеть;
* существующий `audit.jsonl` остаётся как есть — пишем в оба журнала;
* выгрузка во внешнюю систему (Notion) — только офлайн-скриптом, никогда из пути
  обработки запроса;
* наружу уходят только метаданные и сводка; текст вопроса и ПДн — нет.

## Решения

### D1. Отдельный SQLite-журнал `db/sessions.db`, а не расширение аудита

**Решение.** Новая таблица `sessions` (поля ТЗ + служебные `id`, `notion_page_id`,
`exported_at`). Запись — `SessionLog.record()` с коротким соединением на запись,
`journal_mode=WAL`, таймаут 5 с и одним повтором.

**Обоснование.** JSONL не умеет «отметить выгруженное» и требует перечитывания файла
на каждый экспорт; SQLite даёт выборку «новые записи» и устойчивость к параллельной
записи Streamlit + чтению экспортёром. Аудит не трогаем: его формат — контракт для
тестов и внешних потребителей.

**Следствие.** Два журнала живут параллельно; их нельзя путать: аудит — про шаги,
`session_log` — про сессии.

### D2. Точка записи — UI (`app.py`/`app_local.py`), а не диспетчер

**Решение.** Строка пишется в конце блока `if submitted:` — после отрисовки ответа;
`dispatcher.process_request`, граф и `pipeline` не меняются.

**Обоснование.** В `AssistantResult` уже есть всё нужное (`dsl`, `status`, `source`,
`payload`); правка ядра ради журнала нарушила бы границу «детерминированное ядро не
меняется» и добавила бы побочный эффект в тестируемый контракт. Ошибка записи не
может сломать ответ: `record_request` гасит исключения.

**Следствие.** Запрос, упавший необработанным исключением до конца блока, строки не
оставит: журнал фиксирует завершённые сессии, а не аварии процесса.

### D3. `session_id` — новый UUID на запрос

**Решение.** `uuid4` на каждый отправленный вопрос, а не `llm_session_id` чата.

**Обоснование.** ТЗ: «одна строка = одна аналитическая сессия». Идентификатор чата
объединяет несколько запросов и сделал бы выборки по сессиям неоднозначными.

### D4. `fallback` сводится к `status="ok"` + `degraded=true`

**Решение.** В журнале и Notion всего четыре статуса (`ok`/`clarify`/`refuse`/`error`);
ответ на офлайн-правилах вместо LLM — это `ok` с `degraded=true`.

**Обоснование.** `fallback` — не отдельный исход для читателя отчёта, а признак
деградации; пятое значение select сломало бы заявленный контракт свойств Notion.

### D5. `verdict` — «расчёт построен», а не «статус ok»

**Решение.** `verdict=true` только при `status="ok"` **и** наличии `payload`
(результат реально посчитан). Уточнение/отказ/ошибка — `false`.

**Обоснование.** Иначе чекбокс дублировал бы статус и не отвечал на вопрос «получил ли
пользователь ответ».

### D6. Токены — `NULL`, поле остаётся в схеме

**Решение.** `prompt_tokens`/`output_tokens` всегда `NULL`; свойство «Токены» в Notion
не отправляется, если значения нет.

**Обоснование.** `CompletionResult` не содержит usage; токены знает только
`OllamaChatClient.last_usage`. Расширять контракт клиента ради метрики — менять ядро.
Поле оставлено, чтобы появление usage не требовало миграции.

### D7. Fail-safe запись: глотать ошибку, писать в лог приложения

**Решение.** `SessionLog.record` ловит `sqlite3.Error`/`OSError`, делает один повтор,
затем `logger.warning`. Возвращает `bool` — только для тестов и диагностики.

**Обоснование.** Журнал — побочный канал; недоступная БД (блокировка, права, сетевой
диск) не должна превращать успешный расчёт в ошибку.

### D8. Экспорт — скрипт и явная кнопка, Notion вне пути запроса

**Решение.** `scripts/notion_export.py` (CLI) и кнопка «Выгрузить» рядом с «Спросить»
вызывают одну и ту же функцию `onec_analyst.notion_export.export_chat`: она выгружает
сессии **активного диалога** (`chat_id`). Из пути обработки вопроса Notion не
вызывается: кнопка — отдельное действие пользователя, расчёт при её нажатии не
запускается. Ошибка сети/настройки показывается сообщением, а не падением страницы.
Подключение (токен и адреса баз) задаётся локально в окружении разработчика и в
репозиторий не входит.

**Обоснование.** Сетевой вызов внешней SaaS в обработке запроса — источник задержек и
отказов; при этом ручной запуск из терминала неудобен для повседневной работы.
Кнопка даёт контроль («выгрузить сейчас») без автоматического побочного эффекта.

**Следствие.** Кнопка доступна только там, где в окружении есть ключ и id базы; иначе
показывается предупреждение «выгрузка не настроена».

### D9. Идемпотентность выгрузки — колонки-маркеры, а не watermark-файл

**Решение.** `exported_at IS NULL` = «новая запись»; после создания страницы
проставляются `notion_page_id` и `exported_at`. Сбой на записи не останавливает
пачку. Кнопка «Выгрузить» дополнительно фильтрует выборку по `chat_id`, поэтому
повторное нажатие отправляет только новые сессии диалога и не создаёт дублей.

**Обоснование.** Файл-маркер рассинхронизируется с БД и теряет состояние при переносе;
отметка в строке атомарна относительно самого факта выгрузки.

### D10. Санитизация: вопрос — всегда `<PROMPT>`, ПДн — `<PII>`

**Решение.** Текст вопроса не отправляется никогда. Свободные поля (провайдер, модель,
id), текст сводки и названия из результата прогоняются через регулярки
e-mail/телефон/ИНН. Сущности результата (товары, контрагенты) отправляются как есть —
по решению владельца данных: текущие данные синтетические.

**Обоснование.** Вопрос — это формулировка пользователя, её в отчёте быть не должно.
Результат анализа, наоборот, и есть ценность страницы; для реальных выгрузок 1С
предусмотрен отдельный режим маскирования (см. «Последствия»), который включается до
перехода на реальные данные.

### D11. Тело страницы: результат анализа + метаданные + PNG

**Решение.** Свойства — только метаданные. В теле: `heading_2 «Результат»`, текст
сводки, нативная таблица — снимок таблицы результата (колонки переведены на русский:
«№», «Товар», «Выручка без НДС, ₽», «Доля, %»), затем `heading_2 «Сессия»`, таблица
метаданных и PNG. Полные пути к локальным файлам в страницу не отправляются: они
имеют смысл только на машине с журналом; локальная копия пишется в `exports/` молча.
PNG грузится двумя шагами (`file_uploads.create` → `send`): для `single_part` отправка
сама переводит объект в `uploaded`, а `complete` нужен только для `multi_part` и после
`single_part` отклоняется с 400. График рисуется по значениям результата (топ —
горизонтальные столбики по выручке) и только для успешных сессий: у
`clarify`/`refuse`/`error` результата нет, поэтому картинка не строится.

**Обоснование.** ТЗ требует таблицу и график именно в теле, а не в свойствах. Notion не
принимает локальный путь — нужен upload.

### D12. 429: собственный backoff с приоритетом `Retry-After`

**Решение.** Обёртка `call_with_backoff`: при статусе 429 задержка = `Retry-After`
(если есть), иначе `1·2^n` секунд, потолок 60 с, максимум 5 попыток; прочие ошибки
пробрасываются сразу. Встроенный retry SDK отключён (`Client(retry=False)`).

**Обоснование.** Поведение должно быть видно в логах и покрыто тестами без сети;
молчаливый ретрай SDK этого не даёт.

### D13. БД журнала закрыта от публикации на трёх уровнях

**Решение.** `db/`, `exports/`, `*.db` — в `.gitignore`; те же правила в
`.git/info/exclude` (локальная страховка, не публикуется); `db/`, `*.db`, `exports/` —
в `.dockerignore`; тест `test_session_db_is_not_tracked_by_git` падает, если каталог
попал в индекс или перестал игнорироваться.

**Обоснование.** В строке `sessions` лежит текст вопроса; репозиторий публикуется на
GitHub. `.gitignore` — декларация, `info/exclude` — защита от случайного `git add -A`,
тест — защита от регрессии правил.

### D14. Совместимость с API `2025-09-03`: database → data source

**Решение.** База создаётся с `initial_data_source.properties` (9 свойств), из ответа
берутся `database_id` **и** `data_source_id`; страницы создаются с
`parent={"type": "data_source_id", ...}`. На входе (адрес базы из локального
окружения) принимается любой из двух id: скрипт читает базу, берёт первый data source;
при 404/400 считает аргумент уже id источника; для базы без `data_sources` остаётся
старый `parent={"type": "database_id", ...}`.

**Обоснование.** С версии API `2025-09-03` Notion разделил базу и источник данных:
`databases.create` больше не принимает `properties`, а страницы под базой создаются
через `data_source_id`. Библиотека `notion-client` 3.x по умолчанию отправляет
`Notion-Version: 2025-09-03`, поэтому старый вызов `parent={"database_id": ...}` дал бы
ошибку валидации.

**Следствие.** Один и тот же скрипт работает и с новыми базами (data source), и с
базами, созданными до изменения; в лог выводятся оба id.

### D15. Сводка результата хранится в журнале и едет в тело страницы

**Решение.** В `sessions` добавлена колонка `summary` (JSON: `text`, `intent`,
`values`, `periods`, `entities`, `table`), заполняется в UI-хуке из `SummaryPayload`
и снимка `DataFrame` результата (`result_table`, до 20 строк). Существующие базы
мигрируют через `ALTER TABLE ADD COLUMN summary TEXT` при первой записи. Экспортёр
строит из неё блок «Результат» и график по значениям; при отсутствии сводки
(уточнение/отказ) блок не рисуется, а график показывает длительность.

**Обоснование.** Без сводки страница показывала только метаданные сессии и не отвечала
на вопрос «что посчитали». Журнал — единственное место, где результат уже есть в
структурированном виде; хранить его только в UI-памяти нельзя (перезапуск теряет).

**Следствие.** `sessions.db` содержит и вопрос, и результат — это локальные данные,
закрытые от git. В Notion уходит сводка (с названиями сущностей), но не вопрос.

### D16. Сырой ответ модели — только по флагу и только локально

**Решение.** Колонка `raw_response` существует, но заполняется лишь при
`ONEC_SESSION_LOG_RAW=1` (значения `1/true/yes/on`); по умолчанию — `NULL`. Длина
обрезается до 20 000 символов. В выборку для экспортёра поле не входит, поэтому в
Notion сырой ответ не уходит никогда. Промпт (`llm_request`) не хранится вообще.

**Обоснование.** Для tool-calling провайдеров структура ответа уже сохранена в `dsl`;
сырой текст нужен только когда модель вернула мусор (JSON-адаптер Ollama/GigaChat).
Держать это всегда — значит копить в базе копии ответов и вопросы, а промпт ещё и
дублировал бы вопрос целиком.

**Следствие.** Отладка «постфактум» возможна только с заранее включённым флагом;
включение флага меняет объём БД и требует политики хранения.

### D17. История диалога — в SQLite, в Notion только витрина

**Решение.** Журнал хранит связку диалога (`chat_id`, `turn`) и полный текст ответа
(`answer`), который увидел пользователь: сводка, уточняющий вопрос, отказ или ошибка.
`chat_id` — отдельный uuid разговора (не id лимита LLM), `turn` — номер запроса внутри
диалога, оба сбрасываются кнопкой «Новый диалог». В выборку для экспортёра эти поля не
входят: история остаётся локальной.

**Обоснование.** «Вся история» — это не только строка сессии, но и цепочка «вопрос →
уточнение → ответ». Без `chat_id`/`turn` её приходится восстанавливать по порядку
вставки, а он ломается при повторных прогонах и параллельных сессиях. Полный текст
ответа нужен, чтобы разбирать качество без воспроизведения запроса.

**Почему не в Notion.** Лимиты API (100 блоков на страницу, 2000 символов на rich-text,
~3 запроса/с), отсутствие join/агрегатов и внешний периметр: история с реальными
данными 1С — это выгрузка коммерческой тайны в SaaS. Notion остаётся витриной страниц
по сессиям.

**Следствие.** База растёт (полный ответ до 20 000 символов на строку); политика
хранения — бессрочно, ротация при необходимости делается отдельной командой.

### D18. «Ответ модели» — свойство с компактным JSON DSL

**Решение.** В базе появилось свойство `Ответ модели` (rich_text): компактный JSON
`{"intent": ..., "params": {...}}` — ровно то, что вернула модель (для
`clarification` — вопрос и `missing`). Для уже существующих баз добавлен
`--ensure-properties`, исторические страницы дозаполнены. Если DSL нет (старые
строки) — свойство не отправляется.

**Обоснование.** Сырой ответ модели хранится только под флагом
`ONEC_SESSION_LOG_RAW` и в Notion не уходит, а нормализованный DSL есть всегда и
содержит те же интент и параметры. Rich-text в Notion ограничен 2000 символами —
компактная сериализация укладывается в них с запасом.

**Следствие.** В строке базы видно «что поняла модель», не открывая страницу;
полный сырой ответ по-прежнему только локально и по флагу.

## Последствия

* Плюс: продуктовые метрики (доля деградаций, длительность, вердикт) без правок ядра.
* Плюс: внешняя витрина (Notion) не влияет на доступность приложения.
* Минус: две независимые системы журналирования; при добавлении полей нужно обновлять
  и `session_log`, и экспортёр.
* Минус: `prompt_tokens`/`output_tokens` пусты, пока контракт клиента не начнёт отдавать
  usage (осознанно отложено).
* Риск: `sessions.db` содержит текст вопросов и результаты — обязательна политика
  хранения и ротации на стороне эксплуатации (в репозиторий файл не попадает).
* Риск: в Notion уходят названия товаров и контрагентов. Для синтетики это нормально;
  перед реальными выгрузками 1С нужен режим маскирования сущностей (`<ENTITY>`).

## Альтернативы

1. **Расширить `audit.jsonl`.** Отклонено: не даёт выборку «новые с момента экспорта»,
   перечитывание файла, смешение шагов и сессий.
2. **Писать журнал в диспетчере.** Отклонено: побочный эффект в ядре, сложнее тесты,
   нет `latency` и `session_id` UI.
3. **Watermark-таблица вместо колонок.** Отклонено: состояние вне строки, сложнее
   восстановление после частичного сбоя.
4. **Ретраи силами SDK.** Отклонено: не видно в логах/тестах, нельзя проверить
   требование «backoff по `Retry-After`».
