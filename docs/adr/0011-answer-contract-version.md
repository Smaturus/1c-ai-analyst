# ADR 0011: версия контракта ответа

- **Статус:** предложено
- **Дата:** 2026-11-13
- **Контекст:** контракт ответа (`answer_contract.py`) уже обязателен для MCP-клиента:
  период, дата данных, срез, серверные итоги, отказы. Пока версия нигде не объявлена.
  Любое изменение формата (новые строки, переименование полей, порядок блоков)
  потенциально ломает клиентов и приёмочные проверки, а агент может незаметно
  начать интерпретировать ответ иначе.

## Решение

Ввести версию контракта **`Contract-Version: 1`** первой строкой каждого ответа
(успех и отказ):

```
Contract-Version: 1
Период: 01.01.2024–31.12.2024
Данные: выгрузка 12.11.2026 13:32
Срез: total
...
```

Правила:

- в пределах версии допустимы только обратносовместимые изменения
  (добавление строки/колонки, уточнение текста);
- удаление/переименование обязательных полей, изменение семантики периода или
  даты данных — новая версия;
- версия дублируется в описании MCP-инструмента и в аудите (`contract_version`);
- приёмочный тест проверяет наличие версии в каждом ответе и отказе.

**Реализация — следующий шаг**, вне текущего изменения: правка
`answer_contract.format_answer/format_refusal`, тест, запись в аудит.

## Обоснование

1. Интеграция с агентом и внешними клиентами требует предсказуемого формата.
2. Версия в теле ответа видна и человеку, и парсеру (в отличие от версии пакета).
3. Приёмочные тесты фиксируют контракт, а не только цифры.

## Последствия

- Один дополнительный обязательный тест и одна строка в каждом ответе.
- При breaking change — параллельная поддержка двух версий на переходный период.
