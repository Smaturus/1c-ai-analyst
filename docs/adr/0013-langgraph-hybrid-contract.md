# ADR 0013: Гибридный LangGraph-агент — канонический DSL, явный UNKNOWN и политика eval

- **Статус:** принято
- **Дата:** 2026-11-18
- **Связанные решения:** [ADR 0004](0004-llm-json-dsl.md), [ADR 0007](0007-graceful-degradation.md), [ADR 0008](0008-compare-tops-intent.md), [ADR 0012](0012-gigachat-provider.md)
- **Связанные документы:** ТЗ «Гибридная архитектура LangGraph» ревизии 6.3 (исходная) и 6.4 (действующая), `GoldenSet.py`
- **Схема архитектуры:** `ToBeLG_64.png` (исходник `ToBeLG_64.dot`, вектор `ToBeLG_64.svg`) — лежит в папке ТЗ, вне репозитория; исторические `ToBeLG_old.png` и `ToBeLG_md_old.png`.
- **Примечание:** ревизия 6.4 применена 2026-11-18; ссылки на строки ТЗ в разделах D1–D5 относятся к редакции 6.3 и сохранены для трассировки.

## Контекст

Версия 0.7.0 уже содержит почти все строительные блоки агента: 7 интентов,
Pydantic-модели с `extra="forbid"`, `dispatch_intent`, офлайн-правила,
tool calling для GigaChat, лимиты, аудит и 393 теста. ТЗ 6.3 добавляет
LangGraph-агента, память, мета-оценку и GoldSet.

Проблема в том, что материалы описывают **четыре разных DSL**:

1. фактический код — `metric/limit/ascending/freq/group_by/...`;
2. ТЗ 6.3 — `direction/dimension/granularity/metrics/products/...`;
3. `GoldenSet.py` — смесь ТЗ и собственных форматов (`period1: "A_B"`,
   `result_entities` внутри DSL);
4. диаграмма и `pr1–pr4` — четвёртый набор (`TOP_PRODUCTS`, `DYNAMICS`,
   `CUSTOM_FILTER`, `metrics/dimensions`, `retry < 3`).

Если реализовать граф «по ТЗ», не сведя контракт, получится одно из двух:
GoldSet красный либо сломанный контракт `analytics`/MCP и 393 теста. Кроме
того, без явного решения по UNKNOWN и `period2` кейсы 009/010/016/020/042/043
придётся переписывать дважды.

Цель ADR — добавить агентный режим, **не меняя контракт 7 интентов**, и сделать
оценку качества честной и воспроизводимой.

## Решения

### D1. Канонический контракт — текущие Pydantic-модели и `INTENT_PARAMETERS`

**Решение.** Единственный источник истины — `analytics.INTENT_PARAMETERS` и
Pydantic-модели в `llm_agent.py`. Схемы инструментов генерируются из моделей
функцией `build_tools()`; промпт не содержит рукописного списка параметров.
Никаких алиасов внутри Pydantic (`direction`, `dimension`, `granularity`,
`metrics`) не добавляется: несовпадения переводятся на границе (промпт,
GoldSet, eval-адаптер), а не в моделях.

Канонические параметры:

| Интент | Параметры |
|---|---|
| `top_bottom_products` | `metric`, `limit`, `ascending`, `start_date`, `end_date`, `product_filter`, `group_filter` |
| `compare_top_products` | `period1`, `period2`, `top_n`, `metric` |
| `negative_revenue` | `start_date`, `end_date`, `group_by` |
| `timeseries` | `freq`, `metric`, `agg`, `start_date`, `end_date`, `fill_gaps`, `product_filter` |
| `counterparty_dynamics` | `period1`, `period2`, `metric`, `top_n`, `min_abs_delta`, `sort_by`, `only_drops`, `min_base_revenue` |
| `group_dynamics` | `period1`, `period2`, `group_by`, `metric`, `top_n`, `min_abs_delta`, `sort_by`, `only_drops`, `group_filter` |
| `total` | `start_date`, `end_date`, `product_filter` |

Таблица маппинга устаревших материалов:

| ТЗ / GoldSet | Канон | Примечание |
|---|---|---|
| `direction: top/bottom` | `ascending: false/true` | `bottom` → `true` |
| `dimension: product/counterparty` | `group_by` | только `negative_revenue` |
| `granularity: day/week/month/quarter/year` | `freq: D/W/M/Q/Y` | — |
| `metrics: [revenue]` | `metric: revenue` | — |
| `metrics: [quantity]` | `metric: quantity` | у `total` метрики нет |
| `metrics: [revenue_vat]` | — | вне MVP, см. D4 |
| `limit` у `compare` | `top_n` | — |
| `group_filter/product_filter: list[str]` | `str` | только один элемент; несколько — вне MVP |
| `products: list[str]` | — | вне MVP, см. D4 |
| `period1/period2: "2023-01-01_2023-12-31"` | пара дат / список из двух ISO | нормализация на границе |
| `result_entities` внутри DSL | отдельное поле состояния | в DSL запрещено (`extra="forbid"`) |
| `missing: "period"` | `period1`, `period2` или `start_date`/`end_date` | зависит от интента |
| `missing: "products"` | `product_filter` | — |
| `missing: "group"` | `group_filter` | — |

**Обоснование.** Контракт уже используется `analytics`, MCP-сервером,
`guard_decision`, 393 тестами и `check_schema_sync()`. Расширение моделей под
имена ТЗ затронуло бы все слои и нарушило бы обещание «контракт не меняется».
Генерация схем из Pydantic исключает расхождение «промпт ↔ валидатор».

**Правки ТЗ.** §3.1, стр. 49–56 (список инструментов) заменяется схемами,
сгенерированными из моделей; примеры в промпте переписываются на канонические
имена; правило 7 («допустимы только перечисленные интенты и параметры»)
сохраняется, но список берётся из `build_tools()`.

**Последствия.** GoldSet нормализуется под канон; в eval появляется адаптер
«устаревший формат → канон»; `check_schema_sync()` остаётся обязательным;
рукописный список параметров в промпте удаляется.

### D2. UNKNOWN — явные мета-инструменты `clarify` и `refuse` плюс статус решения

**Решение.** В tool calling добавляются два мета-инструмента, не являющихся
аналитическими интентами:

- `clarify(missing: list[str], question: str)` — не хватает данных;
  `missing` — канонические ключи (`period1`, `period2`, `product_filter`,
  `group_filter`, `intent`);
- `refuse(reason: str)` — вопрос не относится к аналитике, содержит инъекцию
  или требует неподдерживаемого расчёта.

Бизнес-инструментов остаётся 7. Модель должна вызвать **ровно один**
инструмент. Ноль вызовов, больше одного вызова или вызов с невалидными
аргументами — это `handle_error`, а не попытка угадать намерение по тексту.
Свободный текст без tool call **не** считается сигналом UNKNOWN.

`AgentDecision` получает явное поле статуса:

```text
ok        — валидный DSL, можно исполнять;
clarify   — нужны данные, есть ClarificationPlan;
refuse    — честный отказ с причиной;
error     — техническая ошибка/невалидный ответ после fix;
fallback  — сработал офлайн-режим (лимит, сеть, отключённая LLM).
```

**Обоснование.** В tool calling нет встроенного «верни UNKNOWN»: свободный
текст — ненадёжный и недетерминированный сигнал, который невозможно
стабильно тестировать и который легко подделать инъекцией. Явные инструменты
дают детерминированную маршрутизацию, проверяемую Pydantic, и позволяют
отличить «не хватает периода» от «это не аналитика».

**Правки ТЗ.** §3.1, стр. 59: «не вызывай инструменты (верни UNKNOWN)» →
«вызови `refuse(reason)`»; §3.1, стр. 61: «верни UNKNOWN» → «вызови
`clarify(...)` или `refuse(...)`»; §2.1: в `AgentState` поле
`decision: Optional[AgentDecision]` включает `status`; §2.2: у
`agent_decision` появляются два исходящих статуса; §5: добавляется тест
«ноль/два tool call → handle_error, free text → handle_error».

**Последствия.** Адаптеры GigaChat и OpenAI-совместимых провайдеров
нормализуют ответ к одному `AgentDecision`; UI отображает `clarify` и
`refuse` разными плашками; `guard_decision` сохраняется как защита от
подмены возвратов антитопом; тесты UNKNOWN перестают зависеть от текста
модели.

### D3. `period2` обязателен для интентов сравнения

**Решение.** В `group_dynamics` и `counterparty_dynamics` параметр `period2`
обязателен. Запрос с одним периодом («а по группам за тот же период?») —
это `clarify(missing=["period2"])`, а не «срез за период». Отдельный интент
«срез за один период» в MVP не вводится.

**Обоснование.** Семантика этих интентов — рост/падение между двумя
периодами. С одним периодом не определено, что считать дельтой; «опциональный
period2» означал бы либо тихую подстановку периода, либо второй смысл внутри
одного интента. По ADR 0007 честнее уточнить, чем угадать.

**Правки ТЗ.** §3.1, стр. 54–55: убрать «опционален» у `period2`; §3.1,
стр. 63: удалить правило «если пользователь не просит сравнения, `period2`
можно не передавать» — оно противоречит обязательности. Кейсы 009 и 016 в
GoldSet переводятся в `clarify` с `missing: ["period2"]`. Для 016
дополнительно фиксируется, что после ответа пользователя запрос всё равно
упирается в неподдерживаемый `product_filter` и получает `refuse` (см. D4);
одношаговый GoldSet проверяет только первый честный шаг — `clarify`.

**Последствия.** Часть кейсов GoldSet меняет тип с `value` на `clarify`;
уменьшается число «успешных» кейсов, но исчезает скрытая подстановка периода.
В UI текст уточнения должен называть именно `period2`, а не абстрактный
«период».

### D4. Границы MVP: `revenue_vat` и произвольные наборы товаров — вне этого этапа

**Решение.** В MVP не поддерживаются:

- `revenue_vat` как метрика (`total.metrics` с НДС);
- `products: list[str]` у `compare_top_products`;
- `product_filter` у `counterparty_dynamics`;
- списки более одного значения в `product_filter`/`group_filter`;
- произвольный «срез за один период» для интентов сравнения;
- средний чек и средняя выручка — `refuse`, а не подмена другим интентом;
- будущий период (позже `today`) — `refuse`; прошлый период вне витрины
  допустим и даёт пустой результат.

Вместо частичной поддержки — честный `refuse(reason)` с объяснением, что
именно не поддерживается. Кейсы GoldSet, требующие этих возможностей,
переводятся в `xfail` или `refuse`:

| Кейс | Было | Стало в MVP |
|---|---|---|
| 033 (выручка с НДС) | `total` с `metrics` | `xfail`: расширение контракта, отдельный ADR в бэклоге |
| 008 (сравнить конкретные товары) | `compare_top_products` с `products` | `refuse`: сравнение произвольного набора товаров не поддерживается |
| 023 (сравнить один товар за два года) | `compare_top_products` с `products` | `refuse` (или замена на `timeseries` по годам, если бизнес согласует) |
| 016 (разрез по контрагентам для выбранных товаров) | `counterparty_dynamics` с `product_filter` | `clarify(period2)` на первом шаге; после ответа — `refuse` из-за `product_filter` |
| 044 (группа списком) | `group_filter: list` | один элемент приводится к строке; несколько — `refuse` |

`revenue_vat` — это не строка в `METRICS`, а колонка витрины, правило
загрузки, `metric` в Pydantic, `INTENT_PARAMETERS`, MCP-инструменты, сводка и
тесты. Это отдельное изменение контракта и отдельный ADR.

**Обоснование.** «Контракт не меняется» — это не лозунг, а условие
совместимости с MCP и 393 тестами. Полуподдержка (например, `revenue_vat`
только в промпте) хуже отказа: модель начнёт генерировать невалидный DSL,
а пользователь получит непонятную ошибку вместо объяснения.

**Правки ТЗ.** §3.1, стр. 56: у `total` убрать `metrics`, оставить
`start_date`, `end_date`, `product_filter`; §3.1, стр. 51: у `compare`
убрать `products`; §3.1, стр. 54: у `counterparty_dynamics` убрать
`product_filter`; §6.2: для `refuse`-кейсов проверять наличие объяснения
причины, а не числа.

**Последствия.** Покрытие GoldSet по «успешным» кейсам снижается; зато
каждый отказ воспроизводим и объяснён. В README/`docs/EVAL.md` появляется
раздел «Что сознательно не поддерживается». Инъекционные кейсы 044/045
остаются: они проверяют, что мета-инструменты и Pydantic не дают модели
выполнить чужую команду.

### D5. Eval: кассеты в CI, live-прогон по вехам, judge отдельно

**Решение.** Три слоя оценки сохраняются, но разделяются по среде и смыслу:

1. **Планировщик (вопрос → DSL).**
   - В CI — replay **кассет на уровне `AgentDecision`**: записанный ответ
     (tool call или JSON) прогоняется через парсер, валидатор, `fix_dsl` и
     маршрутизацию без сети. Кассеты провайдер-независимы: адаптер
     GigaChat/OpenAI приводит ответ к одному `AgentDecision`.
   - Live-прогон 50 кейсов — по вехам и перед релизом, на эталонном
     провайдере/модели. Только он измеряет **качество модели**, а не качество
     парсера.
2. **Исполнитель (DSL → числа).** Unit-тесты `dispatch_intent` на
   синтетической фикстуре с вручную посчитанными суммами — как сейчас.
3. **Ответ (числа и формулировки).** `expected_facts` проверяются все, без
   раннего `return`. Для `value`:
   - ярлыки (сущность, метрика, период) — по тексту сводки;
   - числа — по структурированному payload из `summary.py`, а не по
     отформатированной строке;
   - на маленькой фикстуре (10–12 кейсов) — вручную посчитанные константы,
     чтобы проверка не сравнивала `dispatch_intent` с самим собой.

   `summary.py` возвращает `SummaryPayload(text, intent, params, values,
   periods, entities)`; текст строится из payload, факт-чек читает payload.
   Это проверяет **верность ответа расчёту** (faithfulness), а корректность
   самого расчёта остаётся зоной unit-тестов `analytics` — это разные слои,
   и не надо требовать от eval ловить ошибку в pandas.

4. **LLM-as-judge.** 15 кейсов из `JUDGE_SAMPLE`, бинарная рубрика, отдельный
   провайдер, **не** через `on_llm_call` (не съедает лимит пользователя).
   В CI не входит: это сигнал при изменении промптов, а не абсолютная истина.

**Пороговые значения.** Первый live-прогон фиксирует baseline. Дальше:
CI-гейт — отсутствие регрессии более 3 п.п. и 100% корректная маршрутизация
(ok/clarify/refuse/error) на кассетах; целевые ориентиры live — overall ≥ 85%,
simple ≥ 90%, context ≥ 75%, edge_case и non_analytical — 100% корректного
статуса; факт-чек — 100% по ярлыкам и 100% по числам на фикстуре; judge —
≥ 90% «да» как сигнал. Цифры не выдумываются заранее: после первого замера
они становятся базой для non-regression.

**Обоснование.** «DSL-точность без LLM в CI» иначе превращается в измерение
заглушки. Кассеты проверяют детерминированную часть (парсер, валидатор,
маршрутизация, fix), live — модель. Числа в сводке нельзя проверять
регулярками по строке: запятые, пробелы и «₽» дают ложные срабатывания,
поэтому payload — единственное надёжное место.

**Правки ТЗ.** §5, стр. 101: GoldSet 50–100 кейсов дополняется требованием
кассет и live-прогона; §6.2: `expected_facts` дополняется проверкой чисел по
payload и требованием проверять все факты; §6.3: judge — отдельный провайдер,
не в CI; §6.4: отчёт разделяет CI-replay и live-метрику, добавляет baseline и
non-regression.

**Последствия.** В репозитории появляются `tests/golden/cases.json`,
`tests/golden/cassettes/`, `tests/fixtures/golden_sales.csv`,
`tools/eval_live.py`, `tools/eval_judge.py`, `docs/EVAL.md`. CI не ходит в
сеть; live-прогон требует ключа и бюджета, поэтому запускается вручную или
по расписанию.

## Рассмотренные альтернативы

- **Принять DSL из ТЗ и переписать `analytics`.** Отклонено: меняет контракт,
  MCP-инструменты, 393 теста и обещание совместимости.
- **Оставить свободный текст как UNKNOWN.** Отклонено: недетерминированно,
  не тестируется, уязвимо к инъекциям.
- **Сделать `period2` опциональным и подставлять период из истории.**
  Отклонено: тихая подстановка противоречит ADR 0007; для 009 периода нет
  ни в истории, ни в вопросе.
- **Реализовать `products` и `revenue_vat` сразу.** Отклонено: это два
  изменения контракта, а не «мелкие правки»; вынесено в бэклог отдельными ADR.
- **Живой LLM в CI.** Отклонено: стоимость, флейки, зависимость от сети.
- **Проверять числа регулярками по готовой сводке.** Отклонено: проверяет
  форматтер, а не расчёт; ломается на пробелах и разделителях.

## Ограничения

1. GoldSet в MVP содержит меньше «успешных» value-кейсов: часть переходит в
   `clarify`/`refuse`/`xfail`. Это осознанно: неподдерживаемое поведение
   должно быть видимым.
2. Кассеты проверяют детерминированную часть, а не качество модели. Метрика
   качества планировщика — только live-прогон.
3. Judge — сигнал, а не истина; он не входит в CI и не влияет на гейт.
4. Память хранится в сессии (`ConversationState`), без checkpointer и без
   персистентности между перезапусками; сброс — по «Очистить историю».
5. GigaChat поддерживает один tool call; OpenAI-совместимые могут вернуть
   несколько. Адаптер нормализует к одному, лишние — `handle_error`.
6. `revenue_vat` и произвольные наборы товаров остаются неподдержанными до
   отдельных ADR.
