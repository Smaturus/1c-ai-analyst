# ADR 0008: Интент «Сравнение топов» (L4L) вместо multi-intent

- **Статус:** принято
- **Дата:** 2026-10-25
- **Контекст:** пользователи просят сравнить рейтинги товаров за два периода: «топ-5 за 2023 и отдельно топ-5 за 2024», «кто выпал из топа, кто вошёл». Раньше такой вопрос либо уходил в `clarification`, либо (после graceful degradation) сводился к одному топу за общий диапазон — то есть ответ не соответствовал запросу. Поддержка «нескольких интентов в одном ответе» (multi-intent: две таблицы, два DSL-объекта) требует расширения контракта LLM, схемы и UI и даёт непредсказуемый ответ для бизнес-пользователя.

## Решение

Добавлен **один новый интент** `compare_top_products` (Like-for-Like): одна таблица, два периода, один показатель.

Контракт:

```json
{"intent": "compare_top_products",
 "params": {"period1": ["2023-01-01", "2023-12-31"],
            "period2": ["2024-01-01", "2024-12-31"],
            "top_n": 5, "metric": "revenue"}}
```

Результат (`analytics.compare_top_products`):

| Колонка | Смысл |
|---|---|
| `rank_p1`, `rank_p2` | место в топе первого/второго периода; `NA`, если товар не входил в топ |
| `<metric>_p1`, `<metric>_p2` | сумма метрики за период (выручка без НДС или количество) |
| `delta` | `<metric>_p2 − <metric>_p1`; `NaN`, если товара не было в топе одного из периодов |
| `status` | `new` — вошёл в топ; `lost` — выпал; `up` — поднялся; `down` — опустился; `same` — то же место |

Строки сортируются по месту во втором периоде (выпавшие — в конце). Возвраты и нулевые строки обрабатываются по общей нетто-методике (см. [DATA_CONTRACT.md](../DATA_CONTRACT.md), раздел «Бизнес-правила»).

Интент зарегистрирован в `INTENT_REGISTRY`/`INTENT_PARAMETERS`, Pydantic-моделях, системном промпте, офлайн-правилах, `docs/intent_schema.json` и UI (таблица со статусами + grouped bar).

## Обоснование

1. **Один интент — один предсказуемый ответ.** Бизнес-пользователь получает ровно то, что просил: сравнение рейтингов, а не два независимых дашборда.
2. **Нет multi-intent:** не нужно менять формат DSL (`{"intent": ...}` остаётся один объект), схему Pydantic, контракт `dispatch_intent` и логику UI; LLM по-прежнему возвращает один JSON.
3. **Бизнес-ценность L4L:** сразу видно, кто удержал позиции, кто вырос/упал, кто вошёл в топ и кто выпал — это готовый аналитический вывод, а не сырые числа.
4. **Детерминизм:** функция считается по pandas, LLM только заполняет параметры (принцип [ADR 0004](0004-llm-json-dsl.md) сохранён).
5. **Офлайн-паритет:** правила распознают «сравни топ-5 за 2023 и 2024» и «топ-5 за 2023 и топ-5 за 2024» без LLM.
6. **Убирает суррогат:** для запросов про два рейтинга больше не нужен fallback «один топ за диапазон»; graceful degradation остаётся для прочих неоднозначностей ([ADR 0007](0007-graceful-degradation.md)).

## Рассмотренные альтернативы

- **Multi-intent (массив интентов в DSL, несколько таблиц).** Отклонено для MVP: меняет контракт, схему, промпт и UI, повышает риск несогласованных ответов; L4L закрывает основной сценарий одним интентом. Может быть добавлено позже отдельным решением.
- **Оставить только fallback «один топ за диапазон».** Отклонено: ответ не соответствует вопросу (замечание эксперта).
- **Добавить параметр `compare=True` к `top_bottom_products`.** Отклонено: смешивает семантику одного и двух периодов в одной функции и усложняет схему; отдельный интент читается лучше и в DSL, и в UI.
- **Показывать две отдельные таблицы на уровне UI без DSL.** Отклонено: расчёт стал бы UI-логикой, а не контрактом; тесты и внешние интеграции не увидели бы интент.

## Последствия

- `analytics.py`: новая функция `compare_top_products`, константы `RANK_P1`, `RANK_P2`, `STATUS`, `STATUS_SAME`; существующие сигнатуры не менялись.
- `llm_agent.py`: `CompareTopsParams`/`CompareTopsPlan`, запись в `IntentDSL`, промпт и Few-Shot, офлайн-правило (два периода + слова про топ/рейтинг).
- `app.py`/`app_local.py`: заголовок «Сравнение топов (L4L)», русские заголовки колонок с годами, статусы с цветными маркерами, сводка, grouped bar (два бара на товар).
- Тесты: `tests/test_analytics.py` (6 тестов L4L), `tests/test_planner.py` (4 теста правил/валидации), обновлён `tests/test_clarification.py` (fallback теперь даёт L4L); `smoke_test.py` проверяет 6 интентов, `smoke_llm.py` — 89 проверок.
- Ограничения: сравнение только по товарам (не контрагенты/группы), один показатель за оба периода, `top_n` одинаковый для обоих периодов; `delta` не определена для new/lost; «два независимых дашборда» не поддерживаются.
