# ADR 0017: Выгрузка 1С в отдельную SQLite-БД (архив и SQL-слой)

- **Статус:** принято
- **Дата:** 2026-11-22
- **Связанные решения:** [ADR 0005](0005-onec-export-split.md) (ETL отделён от UI), [ADR 0010](0010-export-timestamp.md) (дата данных из метаданных выгрузки), [ADR 0016](0016-session-journal-notion-export.md) (журнал сессий)
- **Затрагивает:** `src/onec_analyst/analytics_db.py` (новый), `scripts/load_1c_to_sqlite.py` (новый), тесты, документацию

## Контекст

Выгрузка 1С (`1c_export/*.csv`) читается pandas при каждом запуске: `sales_1c_v2.csv` — 7,3 МБ и <N> строк, `nomenclature_1c_v2.csv` — <N> строк. Для аналитики в приложении этого достаточно, но:

* CSV неудобно исследовать SQL-запросами (срезы по операциям, организациям, периодам);
* каждый прогон парсит файл заново;
* нет места, где зафиксировано, **из какой выгрузки** получены данные и какие в ней аномалии.

При этом класть продажи в `db/sessions.db` нельзя: журнал сессий — append-only лог запросов со своей политикой хранения, миграциями и выгрузкой в Notion (ADR 0016). Смешивание сломало бы его метрики, бэкап и ротацию.

## Решения

### D1. Отдельный файл `db/analytics.db`

**Решение.** Две предметные таблицы (`nomenclature`, `sales`), служебная `meta`, индексы по `date`, `product`, `counterparty`, `product_group`. Путь переопределяется `ONEC_ANALYTICS_DB`.

**Обоснование.** Разные жизненные циклы: журнал можно чистить и он выгружается наружу, данные 1С — локальный архив. Отдельный файл не ломает ни схему журнала, ни его тесты, ни экспортёр.

### D2. Полная перезагрузка вместо инкремента

**Решение.** `refresh()` читает оба CSV целиком и в одной транзакции делает `DELETE` + `INSERT`. Повторный запуск не плодит строк.

**Обоснование.** Выгрузка 1С — снимок, а не поток событий: у строк нет надёжного естественного ключа (`registrar` повторяется, номенклатура содержит дубликат имени «Чехол Eta»). Инкрементальная загрузка потребовала бы договора о ключах, которого у выгрузки нет.

### D3. Данные грузятся «как есть», аномалии фиксируются

**Решение.** Ничего не фильтруем при загрузке. В `meta.anomalies` пишется JSON: число строк с датой в будущем, с нулевой/отрицательной выручкой, с нулевым количеством, передачи между организациями, список операций и организаций, дубликаты имён номенклатуры, диапазон дат.

**Обоснование.** Архив должен совпадать с выгрузкой один в один (это проверяется тестом: сумма `revenue_net` в SQLite равна сумме по CSV). Фильтрация — решение аналитика в запросе, а не скрытая правка данных.

**Факты первой загрузки (2026-11-22):** <N> строк, <диапазон вашей базы>; 54 строки с будущей датой (все — «Отчет комиссионера»), 11 062 с нулевой выручкой, 41 с отрицательной, 10 операций, 3 организации, дубликат «Чехол Eta».

### D4. Приложение продолжает читать CSV

**Решение.** `analytics_db` не участвует в обработке вопроса; `onec_source`/`data_loader` не меняются.

**Обоснование.** Переключение источника — изменение ядра и Golden-тестов, требующее сверки «CSV vs SQLite» на всех интентах. Делать это вместе с загрузкой — риск сломать ответы без пользы для текущей задачи.

## Последствия

* Плюс: SQL-срезы по выгрузке без pandas; видно происхождение данных (путь, sha256, время загрузки).
* Плюс: журнал сессий не затронут.
* Минус: два места с данными (CSV — источник, SQLite — архив); расхождение возможно, если забыть перезагрузить — `meta.sales_sha256` позволяет это проверить.
* Минус: файл БД ~10 МБ и содержит реальные контрагентов и суммы — живёт локально, `db/` в `.gitignore`/`.dockerignore`.

## Альтернативы

1. **Грузить в `sessions.db`.** Отклонено: смешение лога и данных, поломка метрик и экспорта.
2. **Инкрементальная загрузка по `registrar`.** Отклонено: ключ не уникален, выгрузка — снимок.
3. **Сразу перевести приложение на SQLite.** Отклонено как отдельный шаг с Golden-тестами.
