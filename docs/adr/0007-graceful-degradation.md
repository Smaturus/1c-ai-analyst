# ADR 0007: Graceful Degradation при неоднозначных и составных запросах

- **Статус:** принято
- **Дата:** 2026-10-25
- **Контекст:** пользователь задаёт вопросы на естественном языке, а DSL поддерживает ровно один интент на запрос (`top_bottom_products` принимает один `start_date`/`end_date`, `compare_periods` — ровно два периода). Вопросы бывают неоднозначными («продажи») и **составными** («топ-5 за 2023 и отдельно топ-5 за 2024»). LLM в таком случае честно возвращает `clarification`, но любое уточнение снова может оказаться составным — без ограничений приложение уходит в цикл уточнений, и пользователь не получает ответа. При этом жёсткий отказ («не понимаю») тоже плох: данные для ответа есть.

## Решение

Три уровня плавной деградации — от самого точного ответа к честному отказу, без падений и без выдуманных чисел:

| Уровень | Ситуация | Поведение | Что видит пользователь |
|---|---|---|---|
| 1. Умный текст | Выбрано уточнение (pills) | `clarification.choose_clarified_text`: вторая часть — полный вопрос → только она; фрагмент («2024 год») → склейка с исходным; спорный случай → LLM-классификатор, ошибка LLM → склейка | Поле, запрос и история совпадают |
| 2. Лимит уточнений | Второе уточнение подряд уже показано | `force_interpretation` — детерминированный разбор правилами (без LLM); при успехе — результат | Жёлтая плашка «Уточнения исчерпаны — показываю как понял: «…»» + таблица/график + JSON в «Технических деталях» |
| 3. Честный отказ | Правила тоже не выбрали интент | Сообщение об ошибке и список доступных вопросов; трейсбека нет | «Уточнения исчерпаны, и однозначно разобрать вопрос не удалось…» |

Правила уровней:

1. **Лимит:** `MAX_CLARIFICATIONS = 2` (счётчик `clarification_rounds` в `st.session_state`). Счётчик растёт при показе уточнения и сбрасывается после результата/ошибки, при очистке поля «✖️» и по кнопке «Очистить историю».
2. **Принудительный разбор — только детерминированные правила**, без вызова LLM: результат воспроизводим, быстрый и не зависит от сети. Если правила выбирают интент — показываем его; если нет — уровень 3.
3. **Смысл подмены не скрывается:** плашка прямо говорит, что запрос интерпретирован, а JSON-DSL и режим расчёта доступны в «Технических деталях».
4. **Числа по-прежнему считает только pandas**; LLM выбирает лишь представление текста (уровень 1) — принцип [ADR 0004](0004-llm-json-dsl.md) не нарушен.
5. **Никаких «пустых» ответов вместо деградации:** при отсутствии данных показывается честное сообщение (см. `filter_by_period`/интенты), а не выдуманные числа.

## Обоснование

1. **Пользователь всегда получает результат или понятное объяснение** — цикл уточнений технически невозможен (максимум два круга).
2. **Graceful degradation вместо исключения:** составной запрос сводится к одному корректному показателю; данные не смешиваются и не выдаются за другой разрез.
3. **Честность:** плашка и «Технические детали» позволяют увидеть, что именно посчитано; пользователь может переформулировать.
4. **Детерминизм fallback:** повторный вопрос даёт тот же результат; тесты не требуют LLM.
5. **Дёшево:** нет дополнительных вызовов LLM на уровне 2; классификатор уровня 1 вызывается только в спорном случае и один раз.

## Рассмотренные альтернативы

- **Бесконечные уточнения** — отклонено: пользователь застревает (наблюдалось вживую на составном запросе).
- **Сразу отвечать правилами при любом уточнении** — отклонено: теряется контекст «пользователь ещё уточняет», ответ может быть не тем.
- **Поддержать составные запросы (два рейтинга) сразу** — отложено: требует расширения DSL/промпта и multi-intent UI; вынесено в кандидаты.
- **Только просить переформулировать** — отклонено: данные есть, отказ не помогает.
- **Скрывать факт вынужденной интерпретации** — отклонено: пользователь может принять неверный разрез за правильный.

## Ограничения (важно для заказчика)

1. **Составной запрос не поддерживается по смыслу.** DSL — один интент на запрос; «два отдельных рейтинга» в MVP не строятся. Fallback сводит такой вопрос к **одному** показателю за общий диапазон (например, «топ-5 за 2023 и за 2024» → топ за 2023-01-01…2024-12-31), а не к «первому периоду» и не к двум таблицам. Это осознанный компромисс, а не ошибка расчёта.
2. **Интерпретация может отличаться от замысла.** Детерминированные правила могут выбрать не тот интент/метрику, что подразумевал пользователь (например, `revenue` вместо `quantity`). Плашка предупреждает; JSON в «Технических деталях» показывает фактические параметры.
3. **Лимит — на сессию UI, не на пользователя.** Счётчик живёт в `st.session_state`: сбрасывается при ответе/ошибке/очистке, переживает F5 и сбрасывается при перезапуске процесса; в БД не сохраняется.
4. **LLM-классификатор уровня 1** работает только при включённой LLM: один вызов, без повторов; при ошибке/мусоре — безопасная склейка (текст, а не числа).
5. **Уровень 2 не вызывает LLM** — если LLM-режим был включён, вынужденная интерпретация всё равно детерминированная (правила), поэтому может отличаться от «стиля» LLM.
6. **Деградация не распространяется на ошибки данных:** битый файл, отсутствующий снимок 1С и т.п. обрабатываются отдельно (`load_dataframe`, `st.error`) — там нет «ближайшего» результата, который можно честно показать.
7. **Частичных результатов нет:** нельзя показать «часть запроса» (например, один из двух рейтингов) с пометкой «вторая часть не поддержана» — только свёртку в один показатель.

## Последствия

- Модуль `clarification.py` — единственное место принятия решения о тексте и принудительной интерпретации; UI (`app.py`) только вызывает его.
- Тесты: `tests/test_clarification.py` (склейка, самодостаточность, LLM-классификатор, `force_interpretation`), `tests/test_app_question.py` (счётчик уточнений, лимит, совпадение поля/истории).
- Для будущей поддержки составных запросов потребуется расширение DSL (multi-intent) и UI с несколькими результатами — новое решение и новый ADR; текущее поведение менять не требуется.
- Формулировки плашек и ошибок — часть UX-контракта: при изменении обновлять тесты и [UI_ACCEPTANCE.md](../UI_ACCEPTANCE.md).
