# ADR 0018: Тестовые артефакты в аналитической БД (программа, результаты, кассеты)

- **Статус:** принято
- **Дата:** 2026-11-22
- **Связанные решения:** [ADR 0017](0017-1c-export-sqlite.md) (analytics.db), [ADR 0016](0016-session-journal-notion-export.md) (журнал сессий)
- **Затрагивает:** `src/onec_analyst/analytics_db.py` (схема), `src/onec_analyst/testing_db.py` (новый), `scripts/load_testing_to_sqlite.py` (новый), тесты, документацию

## Контекст

Итоги проверок живут в трёх местах: книга «Программа тестирования» (57 кейсов),
книга «Результаты тестирования» (сводка + лист на каждую из 5 моделей, 57 строк
каждая) и 50 golden-кассет в `tests/golden/cassettes/*.json`. Книги лежат вне
репозитория, кассеты — в git. Сравнивать модели и разбирать расхождения удобнее
SQL-запросами, чем переключением листов Excel.

## Решения

### D1. Отдельные таблицы в `analytics.db`, а не новый файл

**Решение.** `test_program`, `test_results`, `test_summary`, `golden_cassettes` —
в той же `db/analytics.db`, отдельными таблицами.

**Обоснование.** Это осознанный выбор владельца проекта: один локальный файл проще
для запросов «данные + проверки». Риск «перезагрузка выгрузки сотрёт тесты» снят:
`refresh()` трогает только `nomenclature`/`sales`/`meta`, а тест
`test_refresh_of_onec_data_keeps_test_artifacts` это фиксирует.

### D2. Нормализация книг Excel

**Решение.** Программа: `test_order, test_id, question, predecessor, intent, note`.
Результаты: `test_summary` (модель → кейсы/пройдено/%/ошибки/p50) и `test_results`
(модель + все поля листа). Модель берётся из имени листа. Булевы значения
`True/False/пусто` приводятся к `1/0/NULL` — чтобы `COUNT` и `SUM` не спотыкались.

**Обоснование.** Excel-книги — вход для людей; в БД нужны типы и индексы. `fact_match`
оставлен текстом: в отчётах там бывает не только флаг, но и пояснение.

### D3. Кассеты — разобранные поля + сырой JSON

**Решение.** `golden_cassettes(case_id PRIMARY KEY, source, recorded_at, provider,
model, payload, sha256, file_path, loaded_at)`. `payload` — исходный JSON целиком.

**Обоснование.** Разобранные поля дают фильтры по провайдеру/дате/кейсу, а сырой JSON
позволяет восстановить файл и проверить его целостность по `sha256`. Кассета —
источник истины для replay, терять её структуру нельзя.

### D4. Идемпотентность и частичный импорт

**Решение.** Каждый источник перезаписывает свои таблицы целиком (`DELETE`+`INSERT`
в одной транзакции). Можно импортировать только программу, только результаты или
только кассеты — остальные таблицы не трогаются. Кассеты по умолчанию берутся по
маске `tests/golden/cassettes/test_*.json`, поэтому шаблон `_example_synthetic.json`
не попадает в архив.

**Обоснование.** Выгрузки и книги — снимки; инкрементальная загрузка потребовала бы
ключей, которых нет. Маска исключает служебный файл-пример.

### D5. Происхождение данных фиксируется

**Решение.** В `meta` пишутся путь и `sha256` каждой книги, время загрузки и число
строк; для кассет — время и количество.

**Обоснование.** Книги лежат вне репозитория и могут измениться незаметно; без
хеша невозможно понять, что в БД устаревшая версия результатов.

## Последствия

* Плюс: один SQL-запрос даёт «модель → пройдено → ошибки → p50» и позволяет
  сопоставить кейс программы с результатами и кассетой по `test_id`.
* Плюс: архив переживает перезагрузку выгрузки 1С (проверено тестом).
* Минус: `analytics.db` смешивает прод-данные и тест-артефакты — при экспорте файла
  наружу это надо помнить (файл локальный, в git не попадает).
* Минус: книги Excel не копируются в репозиторий, поэтому импорт требует указать
  их пути (по умолчанию скрипт ничего не находит и честно сообщает об этом).

## Альтернативы

1. **Отдельный `db/testing.db`.** Чище по смыслу, но владелец выбрал один файл для
   запросов «данные + проверки»; при желании переносится сменой `ONEC_ANALYTICS_DB`.
2. **Хранить только сырой JSON кассет.** Отклонено: фильтры по провайдеру/дате
   превращаются в JSON-функции.
3. **Не копировать кассеты (они уже в git).** Отклонено: нужен единый SQL-срез
   «кейс + результат + записанный ответ».
