## 3. Выгрузка из 1С

### 3.1. Требования к лицензии 1С

Для выгрузки данных через `V83.COMConnector` (модуль `onec_analyst.onec_source`)
необходима платформа «1С:Предприятие 8.3» версии **8.3.23 и выше**.

**Не используйте Учебную версию (Learning Version):** в ней отключена поддержка
COM-соединений, поэтому скрипт не сможет подключиться к базе.

**Рекомендуемый вариант — Комьюнити-лицензия (Community License):**

1. Зарегистрируйтесь на портале [`developer.1c.ru`](https://developer.1c.ru/)
   (потребуется подтверждение по SMS).
2. Активируйте лицензию в личном кабинете.
3. Эта лицензия бесплатна и позволяет вести полноценную разработку на одном
   компьютере, включая COM-подключения.

**Ограничение:** Комьюнити-лицензия предназначена **только для разработки и
отладки**. Её нельзя использовать для ведения реального учёта на предприятии.
Срок действия лицензии — 1 неделя, но она продлевается автоматически при
наличии интернета.

### 3.2. Требования к окружению

- 1С установлена, COM-класс `V83.COMConnector` зарегистрирован (64-бит).
- Есть действующая лицензия 1С (файл в `C:\ProgramData\1C\licenses` или ключ).
- У процесса есть **права на запись** в каталог файловой базы: 1С создаёт lock-файлы `*.cfl`/`*.1CL`.
- Python с `pywin32` (`pip install pywin32`).

### 3.3. Команда

Выгрузка бывает двух видов. Оба пишут одни и те же файлы (`sales_1c.csv`,
`nomenclature_1c.csv`), различается только период.

**Режим «период» — эталонные цифры проекта (2022–2024):**

```powershell
python -m onec_analyst.onec_source --base "<путь к базе 1С>" --out-dir .\1c_export `
  --start 2022-01-01 --end 2024-12-31
```

Ожидаемо:

```
Конфигурация: Управление торговлей, редакция 11 11.5.22.77
Записей регистра: 2568
Номенклатуры: 253, товарных групп: 27
Выручка без НДС: 19,313,936.63
Выручка с НДС:   22,957,182.97
Количество:      10,878.000
```

**Режим «полная история» — без `--start`/`--end`:**

```powershell
python -m onec_analyst.onec_source --base "<путь к базе 1С>" --out-dir .\1c_export
```

Ожидаемо на демо-базе (УТ 11.5.22.77, данные 2021-09-01 … 2026-01-20):

```
Конфигурация: Управление торговлей, редакция 11 11.5.22.77
Записей регистра: 3859
Номенклатуры: 253, товарных групп: 27
Выручка без НДС: 27,465,893.44
Выручка с НДС:   32,736,304.12
Количество:      14,362.000
```

> **Что лежит в рабочей копии сейчас (2026-11-12).** В `1c_export/` находится
> **полная** выгрузка: 3859 записей, 2021-09-01 … 2026-01-20, выручка без НДС
> 27 465 893,44 ₽. Подпериод 2022–2024 из этих же данных даёт эталонные 2568 записей
> и 19 313 936,63 ₽. Если нужны именно эталонные цифры — перезапустите выгрузку с
> `--start/--end` либо отфильтруйте витрину по датам. Каталог `1c_export/` в
> `.gitignore` и в публичный репозиторий не попадает.

### 3.4. Если база недоступна на запись

Файловая 1С не откроется без права записи в свой каталог. Варианты:

1. Выдать текущему пользователю права на каталог базы (владелец каталога может это сделать).
2. Работать через копию базы (как в этом проекте): скопировать каталог в рабочую папку и указать `--base` на копию.

```powershell
robocopy "<путь к базе 1С>" ".\1c_base\utdemo" /E /COPY:DAT /R:1 /W:1 /MT:8
# затем --base ".\1c_base\utdemo"
# после выгрузки копию можно удалить (2,9 ГБ)
```

3. Если 1С не может проверить лицензию под ограничениями песочницы (ошибка `0x80041003` / «Не найдена лицензия»), запускать подключение в режиме без файловой песочницы — на обычной машине это не требуется.

## 5. Типовые ошибки и решения

| Симптом | Причина | Решение |
|---|---|---|
| `Не найдена лицензия... Status=-100` | 1С не видит лицензию (песочница/WMI, ключ) | Запуск без файловой песочницы; проверить `C:\ProgramData\1C\licenses`, ключ HASP |
| `Ошибка режима доступа к файлу базы данных` | Нет прав на запись в каталог базы или база занята | Права на запись, закрыть эксклюзивные сеансы, копия базы |
| `Неверно указан пользователь или пароль` | Неверные учётные данные | Для демо-базы: `Администратор`, пустой пароль |
| `com_error ... ВЫРАЗИТЬ` | Недопустимое приведение типа в запросе | Использовать точечную нотацию (`АналитикаУчетаНоменклатуры.Номенклатура`) |
| `This object does not support enumeration` | Обращение к полю результата через `[]` в pywin32 | Читать поля через `getattr(selection, "Имя")` |
| `No module named 'win32com'` | В интерпретаторе нет pywin32 | `pip install pywin32` или запускать выгрузку системным Python |
| Поле `Количество` вернуло метод | Имя поля совпало с методом выборки | Алиас в запросе: `Количество КАК Кол` |
| `pattern contains no capture groups` | pandas 3.0 требует группу в `str.extract` | Шаблон с `(\d{2}\.\d{2}\.\d{4})` |
| `Invalid frequency: ME` | `to_period` не принимает `ME` | Нормализация `ME → M` (уже в коде) |
| Excel-файл не открывается: `BadZipFile` | Файл повреждён или не `.xlsx` | Понятная ошибка `ValueError` в загрузчике |
| ИТС: «Доступ к данному материалу ограничен» | Договор developer.1c.ru не включает документацию продуктов | Зарегистрировать УТ/ERP на Портале 1С:ИТС; методика выручки — [ADR 0001](adr/0001-revenue-net.md) |

### 8.2. Запуск

```powershell
# офлайн-режим (без ключа LLM, детерминированные правила)
.\.venv\Scripts\python -m streamlit run app.py

# с LLM
$env:LLM_PROVIDER = "deepseek"   # openai | deepseek | ollama | gigachat | none
$env:LLM_API_KEY  = "sk-..."
```

Графики в UI — **Altair**: горизонтальные бары для топ/динамики (сортировка по значению, цвет по направлению), линия для временного ряда; подписи осей русские (`Товар`, `Контрагент`, `Период`, `Количество, шт.`, `Выручка без НДС, ₽`).

Проверка LLM-слоя без UI:

```powershell

.\.venv\Scripts\python -m pytest -q                 # 393 passed (все unit-тесты tests/)
.\.venv\Scripts\python -m pytest tests/test_planner.py -q   # только правила → DSL
```

Проверка **живого подключения** к провайдерам (ключ + сертификат + модель),
без генерации токенов:

```powershell
$env:PYTHONPATH = "src"
.\.venv\Scripts\python -m onec_analyst.llm_agent --check
```

```
OK      deepseek: deepseek-chat — доступно: deepseek-flash, deepseek-v4-pro
OK      gigachat: GigaChat-2-Pro — доступно: GigaChat-2, GigaChat-2-Max, GigaChat-2-Pro, ...
```

Ошибка вида `ОШИБКА gigachat: ... — GET /models HTTP 403` при уже прошедшем
OAuth означает неверный базовый URL, а не ключ: адрес API — `https://api.giga.chat/v1`
(префикс `/v1`, без `/api`), как в документации метода
(`GET https://api.giga.chat/v1/models`).

Для GigaChat проверка делает OAuth (ключ + `GIGACHAT_SCOPE` + сертификат НУЦ) и
`GET /v1/models`, а затем сверяет `LLM_MODEL_...` со списком доступных моделей —
именно так ловится «ключ рабочий, но модели нет в тарифе». Названия сравниваются
**по уровню модели**, а не буквально: кабинет печатает `GigaChat Pro`, запрос
принимает `GigaChat-2-Pro`, и это одна модель. Уровень не подменяется:
`GigaChat-2-Max` ↔ `GigaChat-3-Ultra` — разные стоимость и скорость.
Для OpenAI-совместимых провайдеров `GET /models` подтверждает ключ и `base_url`;
состав моделей там не авторитетен (алиасы вроде `deepseek-chat` могут работать,
не появляясь в списке), поэтому доступность модели не оценивается. Код возврата
`1` — хотя бы один провайдер не прошёл. Ключи в вывод не попадают.

### Доступ к моделям GigaChat зависит от аккаунта

Список моделей Freemium в документации Сбера и в личном кабинете может
расходиться: кабинет — истина для конкретного аккаунта. Практический порядок:

1. вписать `LLM_API_KEY_GIGACHAT`, запустить `--check` — он напечатает
   **фактически доступные ключу** модели;
2. выбрать модель **своего уровня** и вписать в `LLM_MODEL_GIGACHAT`
   (как в кабинете: `GigaChat Lite` / `GigaChat Pro` / `GigaChat Max` /
   `GigaChat Ultra` — или официальные ID `GigaChat-2-Pro`, `GigaChat-3-Ultra`);
3. если модель отличается от кода проекта — повторно проверить `--check`.

Дефолт проекта — `GigaChat-2-Pro` (уровень Pro). Выбор уровня влияет на расход
лимита: у Ultra отдельный лимит токенов и другая цена, лимиты уровней не
складываются. Для разбора вопросов про витрину 1С Pro достаточно.

Приёмка UI на 5 контрольных вопросах — [UI_ACCEPTANCE.md](UI_ACCEPTANCE.md).

### 8.3. Настройки LLM

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `LLM_PROVIDER` | `none` | `openai`, `deepseek`, `ollama`, `gigachat`, `none` |
| `LLM_MODEL` | по провайдеру | `gpt-4o-mini`, `deepseek-chat`, `llama3.1`, `GigaChat-2-Pro`; **только для провайдера из `LLM_PROVIDER`** |
| `LLM_API_KEY` | — | ключ API (ollama не требует); для GigaChat — authorization key `base64(client_id:client_secret)` |
| `LLM_BASE_URL` | по провайдеру | OpenAI-совместимый API без `/chat/completions`; **только для провайдера из `LLM_PROVIDER`** |
| `LLM_API_KEY_<PROVIDER>` | — | ключ отдельного провайдера (напр. `LLM_API_KEY_GIGACHAT`) — для нескольких провайдеров одновременно |
| `LLM_MODEL_<PROVIDER>` / `LLM_BASE_URL_<PROVIDER>` | по провайдеру | модель/URL отдельного провайдера |
| `LLM_TIMEOUT` | `60` | таймаут, секунды (общая для всех провайдеров) |
| `LLM_TEMPERATURE` | `0` | температура генерации (общая для всех провайдеров) |
| `LLM_JSON_MODE` | `1` (кроме ollama) | запрашивать `response_format=json_object` (для GigaChat не применяется — tool calling) |
| `GIGACHAT_SCOPE` | `GIGACHAT_API_PERS` | версия API: `PERS` / `CORP` / `B2B` |
| `GIGACHAT_AUTH_URL` | `https://ngw.devices.sberbank.ru:9443/api/v2/oauth` | эндпоинт OAuth-токена |
| `LLM_TLS_CA_BUNDLE` | — | путь к корневому сертификату НУЦ Минцифры (обязателен для облака Сбера); несуществующий путь делает провайдера «не настроенным» |
| `LLM_TLS_VERIFY` | `1` | `0` — отключить проверку TLS (только dev) |

> **Общие имена принадлежат одному провайдеру.** `LLM_MODEL` и `LLM_BASE_URL` —
> сокращения для `<...>_<LLM_PROVIDER>`: провайдер по умолчанию берёт их, а на
> другого выбранного в UI провайдера они **не распространяются** (он получает
> свой дефолт — например, `GigaChat-2-Pro`). Поэтому `LLM_MODEL=deepseek-chat`
> не уходит в GigaChat. Общие `LLM_TIMEOUT`/`LLM_TEMPERATURE` действуют на всех.
> Пустое `LLM_MODEL_GIGACHAT=` — это явное «у GigaChat своя модель»: получит
> дефолт GigaChat, а не модель DeepSeek.

> В сайдбаре есть переключатель **«Провайдер LLM»**: он показывает всех
> поддерживаемых провайдеров, а ненастроенные помечает «— не настроен» (выбрать
> можно, но пока работают офлайн-правила с подсказкой, какого ключа не хватает).
> Настроенные провайдеры держатся одновременно: общий `LLM_API_KEY` (провайдер
> по умолчанию из `LLM_PROVIDER`) + собственный `LLM_API_KEY_<PROVIDER>`
> (например, `LLM_API_KEY_GIGACHAT`). Так DeepSeek и GigaChat доступны в одном
> запущенном приложении.

> **Модель GigaChat выбирается в сайдбаре.** Когда активен этот провайдер, под
> переключателем появляется список **«Модель GigaChat»**: он строится из
> `GET /v1/models` этого ключа (эмбеддинги отфильтрованы по полю `type` — их в
> списке чата нет) и кешируется на сессию. Выбор действует **только в текущей
> сессии** и не записывается в `.env`: приложение не редактирует файл с
> секретами, после перезапуска снова действует `LLM_MODEL_GIGACHAT`. Если список
> получить нельзя (нет сети/ключа/сертификата), селектора нет и работает модель
> из `.env`. Модель из `.env`, которой нет в списке API, показывается первой и
> **не** подменяется автоматически — иначе запрос ушёл бы не тем именем.

> Базовый URL GigaChat — `https://api.giga.chat/v1` (префикс `/v1`, без `/api`).
> Ошибка `403` от nginx при успешном OAuth — признак неверного префикса, а не
> ключа; подробности — в [ADR 0012](adr/0012-gigachat-provider.md).

### 8.4. Типовые ошибки UI

| Симптом | Причина | Решение |
|---|---|---|
| `ModuleNotFoundError: streamlit/pydantic` | зависимости не установлены | `pip install -r requirements.txt` |
| Приложение работает, но всегда «офлайн-режим» | не задан `LLM_PROVIDER`/ключ | задать env и перезапустить |
| «Не удалось разобрать вопрос» | модель вернула невалидный JSON дважды | переформулировать или задать другой `LLM_MODEL` |
| «Нужно уточнение» | в вопросе нет периода/намерения | ответить одним из предложенных вариантов |
| `HTTP 401` от провайдера | неверный ключ | проверить `LLM_API_KEY` |
| `HTTP 403` от nginx при GigaChat, хотя OAuth прошёл | неверный базовый URL (лишний `/api`) | адрес API — `https://api.giga.chat/v1` |
| `Сеть недоступна` | нет доступа к API | проверить сеть/`LLM_BASE_URL`; в песочнице DSH внешние API могут быть закрыты |

### 8.5. Лимиты LLM

Приложение учитывает успешные вызовы LLM в SQLite (`rate_limit.db`, в git не попадает):

| Параметр | Значение |
|---|---|
| На сессию (браузер) | **15** вызовов в день (`MAX_PER_SESSION`) |
| Глобально | **100** вызовов в день (`MAX_GLOBAL`) |
| Файл базы | `rate_limit.db` в корне проекта; путь переопределяется `RATE_LIMIT_DB` |
| Автосброс | при смене календарной даты |
| Ручной сброс сессии | только если задано `RATE_LIMIT_ALLOW_RESET=1` — кнопка в сайдбаре при исчерпанном лимите |

Поведение: при исчерпании лимита сессии — предупреждение и принудительный офлайн-режим правил; при глобальном лимите — красный баннер. Если SQLite недоступен — предупреждение и офлайн-режим, без падения. `session_id` — `uuid4` в `st.session_state` (новая сессия браузера = новый счётчик сессии; глобальный дневной лимит при этом общий).

```text
хост ./                 →  контейнер /app/data
хост (в образе)         →  /app/sample_data.csv   ← демо-витрина UI
хост ./1c_export (опц.) →  /app/1c_export         ← снимок 1С, если смонтировать
```

Следствия:

- UI по умолчанию читает **`/app/sample_data.csv` из образа**, а не файлы с хоста через volume `/app/data`.
- Чтобы подставить свою выгрузку 1С, смонтируйте её в ожидаемый путь приложения, например в `docker-compose.yml`:

  ```yaml
  volumes:
    - ./:/app/data
    - ./1c_export:/app/1c_export:ro
  ```

- Свой CSV/Excel можно загрузить через пункт «Загрузить свой файл» в сайдбаре (файл уходит в процесс UI, путь volume для этого не обязателен).
- Multi-stage `Dockerfile`: `build-essential` есть только на этапе сборки зависимостей; runtime-образ его не содержит.
